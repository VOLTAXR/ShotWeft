# ShotWeft V1.6 Video Engine Decision

P0 records the design. P1 and P2 implement the timeline data, templates, and browser workspace. P3 implements local MP4 rendering and verification. P5 adds standalone audio and ZIP manifest v2. ShotWeft remains at `1.5.0`.

The preview uses native HTML media elements on the project frame clock. Voice and Music accept WAV, MP3, and M4A assets and embedded video audio. The workspace fills missing track kinds with empty rows while retaining each preset's frame rate, dimensions, and track labels. Track-level caption style defaults and template-specific overlay geometry remain proposals.

## V2 M1 additive local evaluation

V1.6's decision below remains the engine for project ZIP rendering. V2 M1 adds a separate DirectorPlan compiler and adapters: `RenderAdapter`, `LegacyFFmpegRenderAdapter` (delegates unchanged ZIP rendering), and `RemotionRenderAdapter`. `CompositionRegistry` is represented by the fixed `compositionRegistry` map; only the trusted `ShotWeftDirector` composition can be selected. Plan JSON never supplies executable code or entry paths.

The same `DirectorComposition` is used in Player and the registered Studio/renderer entry. `calculateMetadata` reads validated plan resolution, rational fps and frame count. Real local Remotion `renderFrames()` captures PNG frames; a validated external LGPL FFmpeg encodes H.264 with `libopenh264` and mixes local audio to stereo AAC. `ffprobe` validates the staged file before no-replace publication. This avoids using Remotion 4.0.546's installed GPL-configured FFmpeg for encoding. Ordinary render temporary files stay under `.tmp` and are removed on success/failure.

M1 graphics/audio scope does not imply V1 timeline parity in Remotion. Existing native preview, V1.6/P5 media import, history, ZIP v1/v2 and `video render`/`video verify` remain their own stable path. DirectorPlan is a separate JSON store. Presenter rendering, footage, slow-push camera, transcription, matching and automated review remain unsupported.

**Remotion is source-available/non-OSI. This branch, Studio and web Player build are local validation only, not a commercial or distribution decision.** Remotion dependencies are development-only and its binaries are not added to the CLI tarball. Source-checkout export is required. See [V2 audit](V2_AUDIT.md), [research](V2_UPSTREAM_RESEARCH.md) and [tests](TEST_REPORT.md).

## V2 M2 project media and persistence

M2 keeps the V1.6 FFmpeg project path and the V2 Remotion composition separate. A project may carry `direction` and/or `video`, but `activeTimeline` selects exactly one editor; they are never synchronized or converted implicitly. DirectorPlan is stored in project history and ZIP manifest v3. Plan assets may carry `projectAssetId` for project/ZIP portability or a safe relative `path` for standalone source-checkout rendering. ZIP v3 validates every linked project asset; path-only plans are not claimed to be portable through a project ZIP.

The shared `DirectorComposition` renders frame-driven images, videos, B-roll layers and captions in both Player and MP4. The renderer copies and probes each local input with realpath confinement, uses measured durations for source ranges, mixes the explicit audio tracks once, and publishes only after ffprobe verification. Project-linked plans require the browser project path; source-checkout CLI rendering requires relative media paths beside the plan.

This is local evaluation only. Remotion is source-available/non-OSI. Presenter/ASR, matting and automatic review remain outside M2. See [M2 tests](TEST_REPORT.md) and [demo](../demos/m2/README.md).

## V1.6 decision

For the V1.6 project ZIP path, use **one render engine**, a user-installed LGPL build of FFmpeg invoked by the local Node.js CLI, with `ffprobe` from the same build for media inspection and output verification. The React/TypeScript editor owns composition and interactive preview. Both the editor and the CLI consume the same validated timeline and share frame arithmetic, layer order, and mute/visibility rules. The CLI renders straight from a project ZIP. The workflow stays offline, and ShotWeft ships no FFmpeg executables or libraries.

| Criterion | Remotion | Motion Canvas | FFmpeg with ShotWeft’s editor |
| --- | --- | --- | --- |
| React composition | React components with frame-based sequences and parameterized compositions | TypeScript generator scenes and its own JSX/Canvas nodes | React owns the editing and preview UI. A shared data model drives the FFmpeg graph. |
| Templates | Published starters and reusable component compositions | Starter projects and reusable scenes | ShotWeft presets expand into tracks, graphics, and caption styles in the same timeline schema. |
| Preview | Studio and embeddable React Player | Vite-powered web editor with live Canvas preview | Existing editor, browser media, and a shared frame clock. |
| Local MP4 | Local render CLI with H.264 output | Canvas image sequences plus optional FFmpeg exporter or external conversion | External process encodes MP4 from local inputs. |
| Audio sync | Frame sequences, trims, and volume through media components | Project audio with an adjustable offset. The optional exporter trims, delays, and mixes scheduled audio. | Normalize timing to frames and audio samples, then trim, delay, and mix. |
| Subtitles | Caption utilities and custom React layouts | Custom timed text nodes | Burn frame-ranged UTF-8 captions and title graphics into the output. |
| Performance | Browser composition and encoding costs. Concurrency is tunable. | Canvas frame drawing. Default image-sequence export adds intermediate writes. | Native filter graph and encoding avoid full-frame browser export. Cost still depends on resolution, input codecs, overlays, and the encoder. |
| License | Proprietary, source-available Remotion License, outside the OSI definition | MIT at repository root. Optional `@motion-canvas/ffmpeg` declares GPLv3. | LGPL 2.1 or later by default. Enabled components and dependencies determine the actual build license. |
| Integration cost | High. Adapt project state and React preview to Remotion’s render lifecycle and review distribution terms. | High. Add a separate Canvas scene model and preview loop, then connect its output to an encoder. | Medium. Build a timeline compiler, media validation, and process adapter while reusing project, editor, and CLI boundaries. |

Remotion has the closest UI framework fit, but adopting it would add a separate composition and rendering lifecycle. Its licensing is scoped to user eligibility and use case, with specific conditions for embedded players, native application distribution, and downloadable project code. Motion Canvas is geared toward code-authored animation, and its core would add a second scene model while still requiring an MP4 encoding path. Its optional exporter also pulls in a static FFmpeg package. The FFmpeg-only export path keeps one timeline model and avoids both engine integrations. The performance assessment is architectural and has no benchmark results at P0.

## Timeline data and compatibility

Extend `Project` with `video?: VideoTimeline`. The existing storyboard keeps its second-based `Shot.duration`, scene and shot order, and references. Initializing a timeline is an explicit user edit. Existing projects open as storyboards, and editing the storyboard does not rebuild a video timeline.

| Record | Proposed fields and rules |
| --- | --- |
| `VideoTimeline` | `schemaVersion: 1`, `fps: { numerator, denominator }`, `width`, `height`, `tracks`, `subtitles`, optional `template`. Use a reduced positive rational frame rate from 1 to 60 fps, including rates such as `30000/1001`. MP4 dimensions are positive even integers, subject to the supported encoder profile. Configure fps before adding timed items. Default to 30 fps unless the applied preset specifies a different rate. |
| `VideoTrack` | Stable `id`, `kind`, `label`, `muted`, `visible`, `clips`. Kinds are `main-video`, `b-roll`, `voice`, `music`, `captions`, `graphics`. One main video track supports sequential clips and gaps. Additional visual tracks stack in array order from bottom to top above main video. Composite caption tracks last, in their array order. Clips may overlap across tracks. Visual clips on the same track and cues on the same caption track cannot overlap. Audio clips may overlap. `visible: false` hides visuals or subtitles. `muted: true` suppresses audio, including embedded audio from video clips. |
| `VideoClip` | Stable `id`, `startFrame`, `durationFrames`, `sourceInFrame`, `sourceOutFrame`, `volume`, `muted`, `label`, `assetId` for media-backed clips, optional `graphic` for layout or text. Main video and B-roll accept video or still images. Voice and music accept audio or the audio stream of a video. Graphics accept still images and generated text or color blocks. Caption tracks carry subtitle cues through their track IDs. Default gain is `volume: 1` and `muted: false`. Gain is linear from 0 to 1. |
| Graphic parameters | Typed image, text, and box variants. Use normalized `x`, `y`, `width`, `height`, and `opacity`, a fit mode (`contain` or `cover`) for images and video, and optional typed text, alignment, font role, size, and color properties. Text and box graphics can be generated without an asset ID. Presets and projects carry data only and cannot specify executable code, paths, or FFmpeg expressions. |
| `SubtitleCue` | Stable `id`, `trackId` referencing a caption track, `startFrame`, exclusive `endFrame`, UTF-8 `text`, optional typed style override. Caption rendering uses a shared default style, then applies the track’s optional `captionStyle` and the cue’s override. |
| `template` | Optional `{ id, revision }` identifying a built-in preset. Preset application writes concrete editable values to the timeline, tracks, and clips. A later preset revision or an unknown preset ID leaves the saved composition usable. |

Frame positions and durations are safe integers with zero-based, half-open ranges. A clip covers `[startFrame, startFrame + durationFrames)` with a positive duration, and a cue covers `[startFrame, endFrame)`. Time for frame `f` is `f × denominator / numerator` seconds. Source in/out points express offsets on the same time grid after normalizing each input’s timestamps to its playback origin. They do not index the source file’s native frames. Timed media plays at 1×, so `sourceOutFrame - sourceInFrame` equals `durationFrames`. Validate the out point against the selected source stream’s duration and handle variable-rate inputs by normalizing to the project rate. Stills and generated graphics use null source in/out points and hold for their whole duration. Timeline length is the largest clip or cue endpoint. Track toggles leave that length stable. Gaps render black with silence, and an empty timeline cannot render.

### Persistence and migration

- The shared core validates timeline fields, track, clip, and cue IDs, track/asset pairings, ranges, and timeline asset ownership. Unknown metadata is preserved. V1.0/V1.5 manifest v1 projects and pre-P5 timeline ZIPs remain readable. The writer selects manifest v2 for a timeline or standalone audio and v1 for legacy-only projects. Older builds require v1. The ZIP manifest version is separate from the timeline’s `schemaVersion`, which remains `1`.
- The ZIP retains `project.json`, `media/<index>/original`, `media/<index>/thumbnail`, and the bundled-photo layout. Each asset ID has one original and one thumbnail regardless of clip count. ZIP allowlist, size, and CRC checks remain in force. Audio assets require a recognized extension and MIME, valid file signature, duration, and image thumbnail. The limit is 60 MiB per audio file. Browser import reads the duration from native audio metadata and checks that playback can decode data. Existing image and video records keep their fields. JSON exports contain metadata, and ZIP exports carry the media.
- Preserve scene and shot IDs on migration, ZIP round trips, and restores. CLI restore preserves asset references and IDs in the new ZIP. Browser restore assigns a fresh project ID and remaps asset IDs, including timeline references, using the same map already used for cover and shot media. Browser duplication uses its existing ID regeneration and remaps all copied media references. To use a legacy bundled photo in the timeline, materialize it once as a local asset with the original bytes. In the same edit, relink existing cover and shot uses to that asset. A V1.6 ZIP writer omits the redundant bundled-photo entry once every reference has migrated.
- IndexedDB keeps its existing tables and indexes. The project edit transaction records timeline edits and standalone audio imports. Undo hides imported audio by asset ID while retaining its bytes for redo. A new history branch removes audio from discarded redo steps. Restoring history explicitly clears an absent `video` field. Trim, mix, and overlay operations leave source bytes intact. Cover history and one-edit bundled-photo relinking remain planned.

## CLI and local rendering

```text
video render <zip> --output <mp4> [--ffmpeg <path>] [--ffprobe <path>]
video verify <zip> [--video <mp4>] [--ffprobe <path>]
```

Register both commands in the existing scoped CLI dispatcher. They stay non-interactive, with one JSON line on stdout for success (`0`) or on stderr for runtime failures (`1`) and usage errors (`2`). `video verify <zip>` validates the ZIP and timeline structurally without requiring either executable. With `--video`, it also checks the existing MP4 against the timeline profile using `ffprobe`. Both video commands return a runtime error for a project without a video timeline. `agent storyboard` and `agent verify` remain the Agent’s non-interactive storyboard and archive workflow. `agent verify` can validate V1.6 ZIP integrity through the shared archive reader.

1. **Resolve executables.** Each tool resolves from its explicit flag, then its `FFMPEG_PATH` or `FFPROBE_PATH` override, then its executable name on `PATH`. An invalid override fails at that setting. ShotWeft invokes executable files with argument arrays and closed stdin. A missing executable reports the corresponding flag and environment variable.
2. **Validate the actual build.** Inspect `-version`, `-buildconf`, and `-L` for both tools. Require a reported GNU LGPL license and reject `--enable-gpl` and `--enable-nonfree`. Check the relevant encoder, decoder, filter, demuxer, and muxer listings. The renderer requires `scale` with `reset_sar`. A two-frame MP4 smoke encode at the requested size and rate tests `libopenh264` and native AAC before rendering the timeline.
3. **Validate and stage inputs.** Reuse `withProject` and the ZIP reader to validate the archive and extract private local copies. The render graph reuses one input per asset. Probe the actual streams, codecs, and duration. Standalone WAV, MP3, and M4A use `wav`, `mp3`, and `mov` respectively and must provide an audio stream. Limit input protocols to `file` and disable external MOV references. Keep graph and text files in the private extraction directory. Bound subprocess time and diagnostic output, clean up temporary files, and preserve source bytes.
4. **Compile video.** Build a black base at the configured fps, resolution, and duration. Use FFmpeg's input rotation handling and normalize timestamps, frame rate, and pixel aspect ratio before placing trimmed visuals. Contain media within the frame and preserve the layer order. Use `drawbox` and `drawtext` for graphics. Burn captions above the graphics with `drawtext` and frame-range expressions. UTF-8 title and cue content goes in literal text files. Local Sans is the default, with a local font file override through `SHOTWEFT_FONT`. Line wrapping and glyph coverage can differ from the browser preview.
5. **Compile audio.** Trim audible source streams on the same clock as video and account for source timestamp offsets. Convert each frame endpoint to its nearest sample on a 48 kHz clock using the shared rational mapping. Resample to stereo, apply gain and mute, and delay each clip by its absolute timeline start in samples. Mix embedded video audio, voice, and music with `atrim`, `asetpts`, `aresample`, `adelay`, `volume`, and `amix`, and limit peaks. Pad or trim against a silent bed for the full video duration. A silent project still exports one AAC stream. Absolute endpoint conversion prevents cumulative timing drift.
6. **Encode, verify, and publish.** Write CFR H.264 (`yuv420p`) and stereo AAC-LC at 48 kHz in MP4 with fast start. Reuse `writeOutputFile` for same-filesystem staging and no-replace publication. Explicitly select the MP4 muxer for its extensionless staging path. Probe the staged regular file with `ffprobe` JSON before publishing. Check the container family and an MP4-compatible brand, since the MOV and MP4 demuxers share a format identifier. Require one H.264 video stream and one stereo AAC-LC audio stream at 48 kHz. Check pixel format, expected resolution and rational fps, decoded video frame count, and video/container duration within one frame. Allow one video frame plus one AAC packet of tolerance on audio duration for sample rounding, AAC priming, and padding. Use the same verifier in `video verify --video` to check stream properties and timeline timing. Successful commands return the absolute `projectPath` and a timeline summary containing fps, resolution, and duration in frames, plus a `video` object with the absolute MP4 path and measured properties when applicable. Publish only after verification, and always refuse an existing output path, including symlinks and aliases to inputs.
